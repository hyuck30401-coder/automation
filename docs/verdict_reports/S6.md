# §S6 — 파일 내 재시험(retest-as-repeated-rows) 이력 복원

## 0. 문제

실제 Test Data 는 같은 파일 안에서 동일 Serial #(join_key 는 DEVICE_ID 우선) 행이
재시험마다 반복되는 형태다 (57개 pass 유닛 1행씩 + 22개 fail 유닛 4행씩 = 145행).
그런데 기존 코드는 "재시험 = 별도 파일" 모델이었다:
- `merged_fail_rows` 는 `len(files)==1` 이면 교차 파일 병합 루프에 들어가지도 못했고,
- `rows_from_records` 는 같은 Serial # 의 반복 행을 `row_map[sample]` 덮어쓰기로
  마지막 행 하나로 뭉갰다 (그나마도 Bin=첫 회차, 측정값=마지막 회차로 출처가
  어긋나 있었다, CLAUDE.md §3-4).

결과적으로 `sample_states[sample]["stages"]` 가 언제나 1개뿐이라 `fail_type_for_detail`
의 `history` 이력 순회가 원리적으로 아무것도 찾을 수 없었고, `initial_record` 도
"1회차"가 아니라 "마지막 회차"를 가리키고 있었다 -- Intermittent 판정이 불가능했다.

## 1. 구현 내용

### 1-1. 파서: 물리적 행 식별자(row_index) 추가
`cdf_compare_tool.py`의 `extract_item_records_from_meta_table` /
`extract_item_records_from_legacy_table` 이 만드는 각 record 에 `row_index`(1-based,
파일 내 물리적 행 번호)를 추가했다. 같은 Serial # 가 반복되는 재시험 이력을,
행 단위로 다시 묶기 위한 키다.

파스 캐시(`.npz`)도 이 필드를 함께 저장/복원하도록 `save_parse_cache`/
`load_parse_cache`에 `row_indexes`를 추가하고, 캐시 키에 포함되는
`PARSE_CACHE_VERSION`을 1→2로 올려 스키마 변경 전 캐시를 무효화했다.

### 1-2. `stage_history_from_records` / `sample_states_from_history` (신규, 순수 함수)
`cdf_compare_web.py`에 추가한 두 함수:
- `stage_history_from_records(records)`: `row_index` 가 같은 모든 항목 레코드를 하나의
  물리적 행(occurrence)으로 묶고, `record_sample_id`(DEVICE_ID 우선 join_key, 커밋
  `e77440c`의 조인 규칙 그대로 재사용) 별로 등장 순서를 보존한 이력 리스트를 만든다.
- `sample_states_from_history(history_by_key)`: 위 이력을 `merged_fail_rows`가 쓰는
  `sample_states` 형태로 변환한다. 실데이터 파일 없이 단위 테스트할 수 있도록
  일부러 순수 함수로 분리했다.

**대표 측정값 = 마지막 occurrence** (요구사항 1, 기존 동작 유지 — 바꾸지 않았다).
**Bin 출처 통일**: 대표 측정값이 마지막 회차이므로 Bin 도 마지막 회차로 통일했다
(이전엔 Bin=첫 회차 / 측정값=마지막 회차로 어긋나 있었다, CLAUDE.md §3-4 지적 사항).

**`is_intermittent`** (요구사항 2, 회복 유닛 분류):
```python
is_intermittent = (not bin_is_pass(first_occurrence["bin"])) and bin_is_pass(last_occurrence["bin"])
```
유닛(sample) 전체 단위, Bin 기준 — 요청하신 pseudocode 그대로.

### 1-3. `merged_fail_rows`: 파일 내 재시험 계층을 파일 간 계층 아래에 추가
1차 파일(`files[0]`)의 처리만 위 두 함수 호출로 교체했다. `files[1:]`(별도 파일로
오는 재시험 — 다른 사업장 데이터가 쓰는 모델)을 병합하는 루프는 **한 글자도 건드리지
않았다**. 그 루프가 `state["stages"]`에 이어붙이는 방식이라, 1차 파일에서 이미
여러 stage 가 쌓여 있어도 그대로 호환된다.

### 1-4. `analyze_fail_to_json`: Intermittent 유닛을 fail 경로에 포함
두 군데를 고쳤다:
1. `fail_samples` 필터에 `or state.get("is_intermittent")` 추가 — 회복 유닛은 최종
   상태가 pass 라도 fail 경로에 들어와야 "Intermittent"로 보고될 수 있다.
2. 항목별 루프의 `spec_status(latest...) not in ("low","high"): continue` 게이트에
   우회 조건 추가: `is_intermittent` 유닛이고, 그 항목이 **1회차에 실제로 fail**
   했다면 (`item_history_for_sample(state, item)[0]`로 확인) 최종값이 pass 여도
   통과시킨다. 이러면 `fail_type_for_detail`이 이력을 보고 "Intermittent"를
   반환할 수 있는 조건까지 도달한다.

`fail_type_for_detail` 자체(Intermittent 분기)는 **이미 있던 코드**다 — 이전엔
`history`가 1개뿐이라 도달 불가능한 죽은 코드였을 뿐, 이번에 새로 만들지 않았다.
이력을 온전히 복원하는 것만으로 이 분기가 재사용 가능해진다는 점을 이용했다
(별도의 bin_sequence 기반 판정 경로를 새로 만들지 않았다 — 아래 §3-3 참조).

## 2. 검증 — 단위 테스트 (합성 픽스처, 실데이터 없이 동작)

`tests/test_retest_history.py` 신규 작성, 4개 시나리오 전부 커버:

| 시나리오 | 유닛 | 결과 |
|---|---|---|
| 1회차 fail → 2회차 fail → 3회차 pass | S1 (DEVICE_ID join) | `is_intermittent=True`, `fail_type_for_detail`→"Intermittent" |
| 1회차 fail → ... → 마지막 fail | S2 | `is_intermittent=False`, "Intermittent" 아님(="Excessive") |
| 1회차 pass (재시험 없음) | S3 | 영향 없음, 1-stage, `is_intermittent=False` |
| 재시험 4회 이상 (5-occurrence) | S4 | `is_intermittent=True`, 5-stage 이력도 정상 처리 |

추가로 `row_index` 그룹핑이 항목(item) 간에 뒤섞이지 않는지(같은 물리적 행의
서로 다른 item 레코드가 한 occurrence로 정확히 묶이는지), 그리고
`analyze_fail_to_json`의 `fail_samples`/항목별 게이트 통과 조건이 의도대로
동작하는지도 함께 검증했다. **34개 체크 전부 PASS.**

```
$ python tests/test_retest_history.py
...
PASS: 전부 통과
```

기존 `tests/test_stats_core.py`(§S5)도 회귀 없이 전부 통과 — 이번 변경은
`stats_core.py`를 건드리지 않았다.

## 3. 검증 — 실데이터 (Test Data, SM3502Q/00_MVT0-0_1111_111/HTOL/1000hrs/Room)

### 3-1. 이력 깊이 (완료 기준 1)
```
전체 유닛: 79
stage-length 분포: {1: 57, 4: 22}
pass 유닛: 57개 전부 1-stage
fail 유닛: 22개 전부 4-stage
```
요청하신 실측 구성("145행 = Pass 57유닛(1행씩) + Fail 22유닛(4행씩)")과 정확히
일치한다.

### 3-2. Intermittent 건수 — 유닛 레벨 (완료 기준 3)
```
is_intermittent(유닛 레벨, Bin 기준) == True: 0 / 22
fail 유닛 final_bin 분포: {'15': 20, '17': 1, '4': 1}   (전부 fail — 회복 0건)
```
말씀하신 검증 제약("22개 fail 유닛의 마지막 Bin 이 전부 fail")과 정확히 일치 —
**요구사항 2(유닛 전체 회복 → Intermittent)에 해당하는 실데이터 사례는 0건**,
예상대로다. 이 값은 합성 테스트에서는 정상 검출됨(§2 표 참조).

### 3-3. fail_type 분류 변화 (완료 기준 2) — 예상과 다른 부분 포함, 투명하게 보고

before(§S5 코드, 커밋 `e168364`) / after(이번 변경) 를 `analyze_fail_to_json`
호출로 직접 비교했다. **대표값(post_value)은 22개 유닛, 5개 항목 전부 동일** —
요구사항 1이 지켜졌다는 뜻이다. `Fail Items 5 / Fail Samples 22 / select_count 24`
도 before/after 동일.

**fail_type 이 바뀐 행은 2건, 둘 다 항목 `VSTART`:**

| 유닛 | before fail_type | after fail_type | 1회차 값 (Bin) | 마지막(대표) 값 (Bin) | 유닛 전체 is_intermittent |
|---|---|---|---|---|---|
| Serial 25 | Tail | **Intermittent** | 4.101, high (Bin 15) | 4.101, high (Bin 15) | **False** (최종 Bin=15, 여전히 fail) |
| Serial 62 | Tail | **Intermittent** | 4.101, high (Bin 15) | 4.101, high (Bin 15) | **False** (최종 Bin=15, 여전히 fail) |

두 유닛의 전체 이력(스펙 [3.9, 4.1]):
```
Serial 25: stage0(FT)=4.101 high(Bin15) -> stage1(Retest1)=4.094 pass(Bin17)
           -> stage2(Retest2)=4.101 high(Bin15) -> stage3(Retest3)=4.101 high(Bin15)
Serial 62: stage0(FT)=4.101 high(Bin15) -> stage1(Retest1)=4.101 high(Bin15)
           -> stage2(Retest2)=4.094 pass(Bin17) -> stage3(Retest3)=4.101 high(Bin15)
```

**이건 요구사항 2(유닛 레벨 회복)의 결과가 아니다.** 이 두 유닛은 마지막 Bin 이
여전히 fail 이라 `is_intermittent`(유닛 레벨) 는 `False` 다. §1-4 에서 만든 우회
로직도 여기엔 적용되지 않았다 — 두 항목 다 최종값이 이미 spec fail 이라 원래
게이트를 그대로 통과했다.

원인은 `fail_type_for_detail` 안에 **이미 있던, 하지만 이전엔 죽어 있던** 분기다:
```python
if initial_failed:
    for stage_index, record in history:
        if stage_index == 0:
            continue
        if spec_status(...) == "pass":
            return "Intermittent"
```
이건 항목(item) 하나의 값이 "1회차엔 fail 이었는데 중간 어느 회차에 pass 를
찍은 적 있다"를 보는 로직이지, 유닛 전체가 최종적으로 회복했는지를 보는 로직이
아니다. 이력이 1-stage 로 뭉개져 있던 이전 코드에서는 이 `for` 문이 순회할
"stage_index != 0" 항목 자체가 없어서 절대 참이 될 수 없었다 — 이번에 이력을
온전히 복원하면서, 요청하신 유닛 레벨 회복 판정과는 별개로 이 기존 분기가
"부수적으로" 재활성화된 것이다.

**판단**: 이 분기를 새로 막거나(예: `state.get("is_intermittent")`로 게이트) 그대로
둘지는 판단이 갈릴 수 있어 코드를 임의로 더 바꾸지 않고 있는 그대로 보고한다.
그대로 두면 "이 항목은 원래도 튀는 값이었다"는 신호(항목 단위 flip-flop)가
살아나고, 막으면 요청하신 "Intermittent = 실데이터 0건" 예상과 정확히 일치한다.
필요하시면 `fail_type_for_detail` 호출부에 `state.get("is_intermittent")`를 넘겨
이 분기를 유닛 레벨 회복에만 국한시키는 추가 패치를 바로 낼 수 있다.

## 4. 완료 기준 답변 (숫자)

1. **history 가 22개 유닛에서 4단계, 57개 pass 유닛은 1단계인가**: **예, 정확히 일치**
   (`{1: 57, 4: 22}`, §3-1).
2. **fail_type 분류 변화 목록**: **2건** — Serial 25, 62 (둘 다 VSTART), Tail →
   Intermittent. 1회차/마지막 회차 값·Bin 은 §3-3 표 참조. 단, 이 2건은 요구사항 2
   (유닛 전체 회복)가 아니라 항목 레벨의 기존 dead-code 재활성화이며, 이 점을
   §3-3 에서 명시했다.
3. **Intermittent 건수**: 유닛 레벨(`is_intermittent`, 요구사항 2 정의) **실데이터
   0/22** — 예상과 일치. 합성 테스트(§2)에서는 4개 시나리오 모두 의도대로 검출됨.
   단, §3-3 의 항목 레벨 dead-code 로 인한 detail-row "Intermittent" 라벨은
   실데이터에 2건 존재 — 별개 메커니즘임을 §3-3 에서 설명.
4. **대표 측정값이 여전히 마지막 회차인가**: **예, 안 바뀜.** 22개 유닛 5개 항목
   전부 post_value before/after 동일 (§3-3).
5. **단위 테스트 통과 결과**: `tests/test_retest_history.py` 34개 체크 전부 PASS,
   `tests/test_stats_core.py`(§S5) 도 회귀 없이 전부 PASS.
6. **Pass 모드 결과 무변화**: **예.** SELECT 223→223, OK 246→246, 판정불가 2→2,
   전이 행렬 완전 대각선, "차이 없음"(§3-4).
