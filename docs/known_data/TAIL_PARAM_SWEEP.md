## 1. 제안 로직을 그대로 걸면 (제안서 기본값 W=0.5, GAP_K=0.5, N_min=1)

| 현재 \ 제안 | Tail | Separated | Shift |

## 2. 어느 파라미터가 실제로 결과를 움직이는가

`N_min` 은 제안서가 지목한 노브지만 실데이터에서는 거의 무의미하고,
**제안서가 0.5 로 고정해 둔 `GAP_K` 가 실질적인 조절 노브**입니다.

각 칸 = 제안 Tail(Marginal) 건수 · 벤치 검토 건수 · 현재 Marginal 과의 일치율

| | GAP_K=0.50 | GAP_K=0.75 | GAP_K=1.00 | GAP_K=1.50 | GAP_K=2.00 |
|---|---|---|---|---|---|
| **W=0.5** | 185 · 1392 · 26% | 225 · 1352 · 32% | 232 · 1345 · 32% | 255 · 1322 · 33% | 255 · 1322 · 33% |
| **W=1.0** | 196 · 1381 · 26% | 328 · 1249 · 46% | 390 · 1187 · 54% | 497 · 1080 · 66% | 516 · 1061 · 67% |
| **W=1.5** | 196 · 1381 · 26% | 328 · 1249 · 46% | 390 · 1187 · 54% | **552 · 1025 · 74%** | 575 · 1002 · 75% |
| **W=2.0** | 196 · 1381 · 26% | 328 · 1249 · 46% | 390 · 1187 · 54% | 552 · 1025 · 74% | 579 · 998 · 75% |

- **W 는 1.0 이상에서 포화**한다 (0.5 → 1.0 에서 185→196, 그 위로는 변화 없음).
  앞서 합성 데이터로 우려했던 "W=0.5 는 너무 좁다"는 실데이터에서는 11건 차이에 불과하다.
- **N_min 은 W 에 종속**이다. W=0.5 에서는 N_min 1/2/3/5 = 184/80/41/**0** 으로 치명적이지만,
  W=1.0 이상에서는 195/195/183/161 로 둔해진다. **W 를 1.0 이상으로 잡으면 N_min 선택이
  결과를 좌우하지 않는다.**
- **GAP_K 가 196 → 579 로 3배를 움직인다.** 이게 실제 노브다.

## 4. 이 로직을 넣어서 실제로 얻는 것

**(가) Shift 128건 — 지금은 전부 Marginal 로 묻혀 있다.**
`IDDQ1` ~ `IDDQ19` 에 항목당 6건씩 몰려 있다. 누설전류라 열화로 **집단 전체가 스펙 쪽으로
밀린** 것이고, 개별 유닛 문제가 아니라 **항목(공정) 신호**다. 유닛별 벤치가 아니라 항목
리뷰로 처리해야 할 건인데 현재는 "이동량이 집단 범위 안"이라는 이유로 접히고 있다.
**파라미터와 무관하게 분리된다** — 이게 도입의 가장 큰 실익이다.

**(나) 앞서 지적한 "한 축만 초과" 구멍이 자동으로 막힌다.**
제안 로직은 Mea_S / Diff_S 를 보지 않으므로 AND 조건 때문에 Slight 에서 탈락하는 일이 없다.

## 5. 결정이 필요한 것

1. **Excessive 우선순위.** GAP_K=1.5 에서 현재 Excessive 57건이 제안 Tail 로 내려온다
   (`HAST/96hrs/Room` 의 `DPH_SEL_L` 등, Gap/한계 0.67). 스펙 이탈률 1% 이상인데 분포
   형상으로는 꼬리인 건이다. **Excessive 를 분포 판정보다 위에 둘지** 정해야 한다.
   (현 우선순위를 유지하면 이 57건은 그대로 Excessive 로 남는다 — 권장)
2. **Shift 를 어디에 표시할지.** Marginal 도 벤치도 아닌 제3의 상태다.
   항목 기준 표에 "집단 이동" 배지를 따로 두는 게 맞다.
3. **벤치 검토 +12% 를 받아들일지.** GAP_K 를 더 키우면 줄어들지만, 2.0 이상에서는
   포화한다(575→579).

## 6. 남은 구현 이슈 (FT_BOUNDARY / TAIL_ANSWER 와 동일)

- Gap 이 항목당 하나 → **유닛 단위 인접-gap walk** 로 바꿔야 다중 이탈이 제대로 갈린다.
- 측정 분해능 추정을 최소 간격 → **간격 최빈값**으로.
- `σ_core = 0`(저분해능) 예외, `Gap == Gap_Limit` 등호 허용오차.
- Core 정의(전 유닛 vs pass 유닛) 합의 — 이 스윕은 **전 유닛** 기준이다.
  payload 에는 전 유닛 값이 한 곳에 없어 `pass_post_values + details[].post_value` 로 합쳤다.

## 부록 — 현재 Tail 이 제안에서 Separated 로 가는 358건의 성격 (W=1.0, GAP_K=0.5)

```
Gap/한계  최소 0.33 · 하위10% 1.05 · 중앙 1.72 · 상위10% 2.8 · 최대 1593
  < 1.2배 : 118건 (33%)      < 2.0배 : 202건 (56%)
  < 1.5배 : 150건 (42%)      < 3.0배 : 332건 (93%)
  그중 Near-Spec Pass 0개라서 탈락: 88건
```

중앙값이 1.72 배 — **임계 바로 위에 몰려 있다.** 합성 데이터(KNOWN02)에서는 Tail 과
Separated 가 확실히 갈렸지만, 실데이터의 현재-Tail 집단은 경계에 붙어 있어 파라미터에
민감하다. GAP_K 를 0.5 → 1.5 로 올리면 이 358건 중 314건이 Tail 로 돌아온다.


## 7. 정정 — 평가 기준을 바꾼다

### 왜 정정하나

3항에서 `GAP_K = 1.5` 를 권한 근거는 "현재 판정과의 일치율 74%" 였다. 그런데 이 작업의
출발점은 **현재 로직에 구멍이 있다**는 것이었다(한 축만 임계를 넘은 건이 Marginal 로
빠지는 문제). 고장난 분류기를 재현하도록 파라미터를 맞추는 건 순환 논증이다.
**재현율은 목표가 아니다.**

### 올바른 눈금 — 그 항목 꼬리의 자연 간격

"연속적인 꼬리"의 물리적 정의는 *Spec Out 값이 마지막 Pass 값에서, Pass 값들끼리
떨어져 있는 정도만큼만 떨어져 있다* 는 것이다. 그래서 비교 대상은 σ_core 가 아니라
**그 항목 가장자리의 인접 간격**이다. 실데이터(항목당 유닛 중앙 63개)에서 재면:

| | / σ_core |
|---|---|
| `g_last` 맨 끝 두 Pass 값 사이 간격 | 하위10% 0.05 · **중앙 0.25** · 상위10% 1.11 |
| `g_edge` 가장자리 5간격의 중앙 | 하위10% 0.07 · **중앙 0.14** · 상위10% 0.33 |

정규 분포 이론값도 비슷하다 — 최상위 순서통계량의 기대 간격은
`1 / (n · φ(z_n))` 로 n=63 이면 0.45 σ, n=231 이면 0.39 σ 다. **n 이 60~230 범위에서
0.4 σ 안팎으로 안정적**이다.

→ **제안서 기본값 `Gap_Limit = 0.5 σ_core` 는 자연 간격의 약 1.2~2배로, 이미 적정하다.**
3항에서 권한 1.5 σ_core 는 자연 간격의 **6배** — 10 걸음 떨어진 점을 "이어져 있다"고
부르는 셈이라 근거가 없다. 철회한다.

### 그 눈금으로 본 현재 Marginal

| | 건수 | Gap / g_last 중앙 | Gap ≤ 1배 | ≤ 2배 | ≤ 3배 |
|---|---|---|---|---|---|
| 현재 Tail (= Marginal) | 503 | **3.7** | 40건 (8%) | 165 (33%) | 215 (43%) |
| 현재 Excessive | 758 | 203.7 | 0 | 16 (2%) | 25 (3%) |
| 현재 Slight | 33 | 24.4 | 0 | 2 (6%) | 3 (9%) |

**현재 Marginal 503건 중 "꼬리가 실제로 이어져 있는" 건은 8% 뿐이다.** 나머지는
집단 끝에서 자기들끼리 벌어진 간격의 몇 배씩 떨어져 있다. 즉 현재 로직이 41.8% 를
Marginal 로 접고 있던 것 자체가 과했고, 제안 로직 기본값이 185건만 남기는 게
오히려 타당하다.

### g_edge 를 직접 Gap_Limit 으로 쓰면 안 된다

자연 눈금이 옳다고 해서 `Gap_Limit = C × g_edge` 로 바꾸면 안 된다. 순서통계량의
인접 간격은 **지수분포**라 변동계수가 1.0 이다 — 한 번의 실현값을 기준으로 쓰면
너무 흔들린다. KNOWN02(정답이 있는 합성 데이터)로 확인:

```
정답 Tail      13건 : Gap / g_edge 중앙 3.9 · 최대 12.7
정답 Sep/Shift 11건 : Gap / g_edge 중앙 9.0 · 최소  0.2      ← 완전히 겹친다
```

g_edge 는 **눈금을 검증하는 용도**로만 쓰고, 판정식 자체는 σ_core 기반을 유지한다.
σ_core 는 표본 전체에서 오는 값이라 훨씬 안정적이다.

### 정정된 권장값

**W = 1.0 ~ 1.5 σ_core · GAP_K = 0.5 (제안서 그대로) · N_min = 1**

| | Marginal | 벤치 검토 |
|---|---|---|
| 현재 | 659 | 918 |
| 정정 권장값 | **196** | **1,381 (+50%)** |

W 만 0.5 → 1.0 으로 올리는 이유는 성능이 아니라 **안정성**이다. W=0.5 에서는 N_min 을
1 에서 2 로만 올려도 Tail 이 184 → 80 으로 반토막 나지만, W ≥ 1.0 이면 195 → 195 로
둔감해진다. Gap_Limit 은 손대지 않는다.

### +50% 를 어떻게 볼 것인가

로직이 과하게 잡는 게 아니라, **지금까지 41.8% 를 잘못 접고 있었다**는 뜻으로 읽어야
한다. 다만 실무 부담은 실재하므로 완화책은 파라미터가 아니라 **분류 자체**에 있다 —
Shift 128건(IDDQ1~19)은 유닛별 벤치가 아니라 **항목 단위 리뷰** 한 건으로 묶인다.
그러면 실제 늘어나는 유닛별 벤치는 1381 − 128 = 1,253건, 현재 대비 +36% 다.

## 8. 구현 반영 (R-043)

`cdf_compare_web.py` 에 반영했다. **기본값은 legacy 라 켜기 전에는 판정이 하나도 안 바뀐다**
(CLAUDE.md §5-1). 환경변수로만 켠다.

```
CDFTOOL_TAIL_MODE=shape          # 켜기 (기본 legacy)
CDFTOOL_TAIL_W_K=1.0             # Near-Spec Zone 폭 계수
CDFTOOL_TAIL_GAP_K=0.5           # Gap_Limit 계수
CDFTOOL_TAIL_RES_K=3.0           # 분해능 계수
CDFTOOL_TAIL_N_MIN=1
```

exe 로 쓸 때는 바로가기나 배치 파일에서 지정한다:
```bat
set CDFTOOL_TAIL_MODE=shape
CDFCompareToolHTML_Rev0.031.exe
```

### 들어간 것

- `tail_shape_verdict(values, LL, UL)` — 항목 하나의 분포 형상을 보고
  `"Tail" / "Separated" / "Shift" / None` 을 돌려준다. Median·MAD 기반이라 이탈값이
  섞여 있어도 중심이 흔들리지 않는다. 상·하한을 따로 보고 둘 다 이탈이면 더 심한 쪽을 쓴다.
- `fail_type_for_detail(..., shape_verdict=...)` — Excessive 까지의 우선순위는 그대로 두고
  (이탈률 1% 이상은 형상과 무관하게 Excessive) 그 아래를 형상 판정으로 대체한다.
  형상 모드에서는 `Slight` 가 나오지 않는다.
- 형상 판정은 **항목 단위라 유닛 루프 밖에서 한 번만** 계산한다.
- `FAIL_TYPE_PRIORITY` 에 `Shift`(3) · `Separated`(5) 추가. 기존 유형끼리의 상대 순서는
  그대로라 legacy 모드의 `worst_fail_type` 결과는 변하지 않는다.
- `FAIL_MARGINAL_TYPE = "Tail"` 그대로 — 새 Tail 이 곧 "정상 산포 끝이 넘어간 것" 이라
  Marginal 정의와 정확히 맞는다.

### Core 모집단 — 여기서 결과가 두 배 갈렸다

형상 판정의 Core 는 **그 항목의 전 유닛**이어야 한다. 그런데 payload 는 이걸 한 곳에
주지 않는다:

- `post_records` 는 **규격을 벗어난 행만** 남긴다
- `pass_post_values` 는 **규격 안 pass 유닛만** 담는다
- 그래서 *다른 항목 때문에 Bin fail 인데 이 항목은 정상인 유닛* 이 양쪽에서 다 빠진다

처음에 이 둘만 합쳐서 판정했더니 실데이터 Marginal 이 **173건**이었는데, 빠진 유닛까지
모아 제대로 된 모집단으로 재니 **345건**이 됐다. 두 배 차이다. 그래서 두 루프에서
`shape_pool` 을 따로 모은다.

### 남은 것

- `Shift` 를 UI 에 어떻게 드러낼지 (지금은 fail_type 문자열로만 나온다). 항목 기준 표에
  "집단 이동" 배지를 따로 두는 게 맞다.
- Gap 이 항목당 하나 → 유닛 단위 인접-gap walk (다중 이탈 항목에서 먼 건까지 Tail 이 된다).
